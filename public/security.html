Security and threat model

What DarkP2P protects, from whom, and where the protection stops. Every statement here describes the published source code.

Summary

  • File contents, names and types are encrypted in the browser with AES-256-GCM. The keys come from a 256-bit secret in the share link's fragment, which is never sent to the server.
  • The server does not store files. In relay mode it forwards encrypted frames through memory.
  • The server does see network metadata: addresses, timing and, in relay mode, sizes.
  • A direct connection shows each peer the other's IP address.
  • The share link is the only credential. Anyone who has it can take part.
  • You have to trust the JavaScript the site serves, and your own device.

What the signaling server can observe

Every transfer starts with both browsers connected to the signaling server, so its operator is in a position to see:

  • IP addresses of both peers, as with any website. The server uses them for rate limiting only, as a hash salted with a random value that is created at start-up and never saved. Its logs contain no addresses.
  • The room ID and when each peer joins and leaves.
  • The WebRTC setup messages it forwards. These contain each browser's network addresses (ICE candidates), which can include local addresses.
  • Whether a peer presented a Pro token.

It cannot see the secret, so it cannot decrypt anything, and for a direct transfer it sees no file data and no file size at all.

The server writes nothing to disk. Its log lines are start-up messages, errors and a periodic line of counters (connections, rooms, relayed megabytes). The reverse proxy in front of it is configured without an access log. These are properties of the configuration in the source repository; as a visitor you cannot verify what a running server logs.

A signaling server could try to place itself between two peers by altering the WebRTC setup messages. That defeats WebRTC's own encryption but not DarkP2P's, because the server does not have the secret. The peers would fail to confirm their session keys and no file could be sent.

What the WebSocket relay can observe

The relay is the same server. When a room uses it (always in Tor Browser, or when a direct connection fails or you force it), the server additionally handles the encrypted frames, and so sees:

  • the size, number and timing of frames, which reveals the approximate file size and who is sending;
  • each frame's unencrypted header: a type byte, a random per-file ID, a chunk number and the IV.

It cannot see file contents, names or types. Frames stay in memory only until they are delivered.

No forward secrecy on the relay path. All keys are derived from the link secret. If someone records the encrypted frames and later obtains the share link, they can decrypt the recording. The relay operator is the party best placed to record. Treat the link as a secret for as long as the file matters, and use a new link for each transfer.

What the STUN and TURN servers can observe

On darkp2p.com, STUN and TURN are provided by a coturn server run by the same operator, not by a third party.

  • STUN is contacted by every browser that attempts a direct connection. It sees that browser's public IP address and nothing about the transfer.
  • TURN is used only in Pro rooms, when no direct route exists or a peer has ticked Hide my IP from peer. It sees both peers' addresses and the volume and timing of the traffic it relays. The traffic is DTLS-encrypted WebRTC with DarkP2P's AES-256-GCM layer inside, so it cannot read it.

coturn's logging is switched off in the deployment configuration, because its logs would contain client addresses.

If you self-host without configuring your own STUN or TURN server, the software falls back to a public Google STUN server, which then sees your users' IP addresses. The server prints a warning when it starts in that state.

What your peer can observe

Your peer receives the files you send, with their names, sizes and types. Beyond that:

A direct WebRTC connection exposes your IP address to your peer, and theirs to you. This is how WebRTC finds a route, and DarkP2P does not hide it by default. The status badge reads "IP EXPOSED TO PEER" when this is the case.

You can avoid it in three ways:

  • Force WebSocket relay. Tick it before your peer joins. Your browser then never starts WebRTC, and your peer only ever talks to the server. The relay's size and speed limits apply.
  • Hide my IP from peer (needs a Pro token). Your browser offers only TURN routes.
  • A VPN or Tor Browser. Your peer and the server see the VPN's or Tor's address.

Each of these protects only the peer who uses it. If your peer connects normally, their browser may still send its addresses.

What someone with the share link can do

The link contains both the room ID and the secret. There are no accounts and no other check, so "Peer key verified" means only that the other side has the same link.

  • Anyone with the link can join the room while one of its two seats is free. If they join before the person you intended, they are your peer: they are offered whatever you send, and can offer you files (you must accept each one).
  • The link keeps working after a transfer. The same room ID and secret can be used again later by anyone who has it.
  • Someone with the link and a recording of the encrypted frames can decrypt them, as described above.

So send the link over a channel you trust, do not post it publicly, and open the site without a link to get a fresh one for each transfer. The link is also stored wherever your browser and your messaging app keep addresses, such as history and chat logs.

Out of scope

DarkP2P does not protect against the following.

  • A compromised device or browser. Malware, a hostile browser extension or someone with access to your machine can read the link, the files and the screen.
  • Malicious JavaScript from the server. The encryption runs in code that the site delivers on every visit. An operator, or someone who has taken over the server, could deliver code that sends the secret elsewhere. This is true of every web application that encrypts in the browser. The page loads no third-party scripts and is served with a Content Security Policy that allows only its own inline script, which limits who can do this to whoever controls the server. If that is not enough, review the source and host it yourself.
  • Traffic analysis. A network observer can see that you connect to DarkP2P and how much data moves.
  • A dishonest peer. Nothing stops the receiver from sharing the file, and nothing checks what a sender offers you. Only accept files from people you trust.
  • Payments. Pro tokens are bought through a third-party payment processor, which has its own records. A token is stored in your browser's local storage and is not tied to an identity by DarkP2P.
  • Traces on your device. Received files, browser history and, briefly, temporary files in the browser's private storage.

Source code

DarkP2P is open source under the MIT licence: github.com/Mklevns/darkp2p. The client is a single HTML file with no build step and no third-party libraries, and the README documents the wire format. You can run your own instance with Docker.

Reporting a vulnerability

Email admin@darkp2p.com with a description and steps to reproduce. Please allow time for a fix before publishing details.

Abuse

DarkP2P does not store or host files, and the operator cannot see what is transferred. See the abuse statement for what that means for reports and requests. Contact: admin@darkp2p.com.
