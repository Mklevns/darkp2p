How DarkP2P works

What happens between opening the page and a file arriving in the other browser, and which machine sees what at each step.

1. The key is made in your browser and lives in the URL fragment

When you open the page without a link, your browser generates two random values with the Web Crypto random generator: a 16-byte room ID and a 32-byte (256-bit) secret. Both are written into the part of the address after the #:

https://darkp2p.com/#<room ID, 32 hex characters>:<secret, base64url>

That address is the share link. Whoever opens it gets the same room ID and the same secret.

The part of a URL after # is called the fragment. Browsers use it locally and leave it out of the requests they send, so it is not in the HTTP request for the page and not in the WebSocket handshake. The page then sends the room ID to the server on purpose, so the server can pair the two browsers. It never sends the secret.

The secret is not used directly. Each file gets its own AES-256-GCM key, derived with HKDF-SHA256 from the secret, a random ID for that file, and two random values the browsers exchange when they connect.

2. Signaling: the server introduces two browsers

The page opens a WebSocket to the server it was loaded from and sends a join message with the room ID. The server keeps the room in memory. A room holds at most two peers, and a third is told the room is full.

When the second peer joins, the server tells both that they are paired, which of them starts the connection, and which STUN (and, for Pro rooms, TURN) servers to use. From then on it forwards the WebRTC setup messages between them: the offer, the answer and the ICE candidates. It copies only the fields it knows and drops anything else.

Rooms exist only in the server's memory and disappear when the last peer leaves. Nothing about a room is written to disk.

3. The direct path: a WebRTC DataChannel

With the setup messages exchanged, the two browsers try to connect to each other directly. If that works, an ordered WebRTC DataChannel opens between them, and file data goes from one browser to the other without passing through the DarkP2P server.

WebRTC already encrypts the channel with DTLS. DarkP2P adds its own layer on top, because the server that forwards the setup messages could otherwise interfere with that encryption:

  • Each side sends a hello with a fresh random 32-byte value, encrypted under a key derived from the link secret. A side that cannot decrypt the other's hello shows "Key mismatch" and file selection stays disabled.
  • Both sides derive the session keys from the secret and both random values, and confirm them to each other. Only then can a file be chosen.
  • The file is read from disk in 16,000-byte chunks. Each chunk is encrypted with AES-256-GCM under a fresh random 12-byte IV. The frame type, the sender's role, the file's ID and the chunk number are authenticated with it, so a chunk cannot be moved, replayed, reordered or reflected without failing.
  • The file's name, size and type travel in an encrypted frame too.

The receiver sees the offer and has to accept it before any data is sent. During the transfer the receiver acknowledges every 64 chunks, and the sender keeps at most 256 chunks unacknowledged, so a slow receiver slows the sender down instead of filling memory. At the end the receiver checks that the number of chunks and bytes matches what was announced, and the sender shows "Delivered" only after the receiver confirms it saved the file.

Both tabs have to stay open until the transfer finishes. There is no upload to resume later.

4. The fallback: an encrypted WebSocket relay

A direct connection is not always possible. The page switches to the relay when:

  • the browser has no WebRTC at all, which is the case in Tor Browser;
  • you tick Force WebSocket relay;
  • no DataChannel has opened 12 seconds after pairing;
  • the WebRTC connection fails.

Either peer can trigger the switch, and both then use the relay. The same encrypted frames are sent as binary messages over the WebSocket that was already open for signaling, and the server passes each one to the other peer. The peers run the hello exchange again, so the relay gets new session keys.

What the relay can see

  • The IP address each peer connects from (for a Tor user, the Tor exit, or nothing on the onion service).
  • The room ID, and when frames are sent.
  • The size and number of the encrypted frames, which gives away the approximate size of the file.
  • The unencrypted frame header: a frame type, the random file ID, the chunk number and the IV.

What it cannot see

  • The secret, because it is never sent.
  • The contents of the file, or its name and type.

The relay has limits that the direct path does not. A room can relay 50 MB in total, counting both directions, until both peers have left it (500 MB if either peer has a Pro token). Each sender is held to about 1 MB per second (4 MB per second in a Pro room). Only a limited number of rooms can use the relay at once; others are told it is busy and the page retries by itself. A room that relays nothing for about six minutes gives its place back, and the page then shows a paused relay that one click resumes. Frames are held in the server's memory only while they wait to be delivered, and are never written to disk.

5. Receiving large files without filling memory

Where the received data goes depends on what the receiving browser supports. The page tries these in order:

  1. A file you choose. If the browser has a save-file picker, accepting the offer opens it, and chunks are written straight to that file.
  2. The Origin Private File System (OPFS). Otherwise chunks are written to a temporary file in the browser's private storage for this site. When the transfer is complete the file is handed to the browser as a normal download, and the temporary copy is deleted a minute later. Temporary files left behind by a closed or crashed tab are removed on a later visit once they are a day old.
  3. Memory. If neither is available, chunks are kept in RAM and saved at the end. This mode is limited to 512 MB, and a larger file is declined automatically.

The offer shows which mode will be used. The sender never loads the whole file either: it reads one chunk at a time.

The server sets no size limit on direct transfers. In practice the limit is the receiver's free disk space and, for OPFS, the storage the browser allows the site.

6. When TURN is used

STUN lets a browser learn its public address so that two browsers behind ordinary home routers can find each other. Some networks, such as strict corporate firewalls and carrier-grade NAT, block that. A TURN server solves it by relaying the WebRTC traffic.

  • Free rooms get a STUN server only. If the direct connection fails, they fall back to the WebSocket relay described above.
  • If either peer in a room has a valid Pro token, both peers also get short-lived TURN credentials. WebRTC then uses TURN when it finds no direct route.
  • With a Pro token you can tick Hide my IP from peer. Your browser then offers only TURN routes, so your peer sees the TURN server's address in place of yours. If TURN is not available, the page refuses to connect instead of falling back to a direct connection.

The TURN server relays the DTLS-encrypted WebRTC stream, and DarkP2P's AES-256-GCM layer is inside that. It sees addresses and traffic volume, not content. It has no per-room byte cap like the WebSocket relay, only its own bandwidth and session quotas.
