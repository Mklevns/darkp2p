Using DarkP2P in Tor Browser

Tor Browser has no WebRTC, so DarkP2P sends the same encrypted frames through its WebSocket relay instead. It works, with a size cap and lower speed.

How to use it

  1. Open DarkP2P in Tor Browser. JavaScript has to be enabled, because all encryption runs in the page. Tor Browser's "Safest" security level turns JavaScript off, and the page cannot work there.
  2. Copy the share link and send it to your peer over a channel you trust.
  3. Your peer opens the link. They can use Tor Browser or an ordinary browser.
  4. The page detects that WebRTC is missing and switches both sides to the relay. The badges read "TUNNEL: E2E WS RELAY" and "IP MASKED FROM PEER".
  5. Once the page reports that the peer key is verified, choose a file. Your peer accepts it, and both tabs stay open until it is delivered.

Onion service. This site is also reachable inside the Tor network, without leaving through an exit node:

http://{{ONION_HOST}}/

Tor Browser also offers it through the ".onion available" button in the address bar. A link made on the onion address points to the onion address, so your peer needs Tor Browser to open it as it is. The part after # works on either address.

This deployment does not publish an onion address. Tor Browser reaches it through a Tor exit node, like any other website.

Why WebRTC is not available in Tor Browser

Tor Browser is built without WebRTC. WebRTC is designed to discover a device's real network addresses and to connect peers directly, mostly over UDP. Tor carries TCP only, and a direct connection would bypass Tor and reveal the address Tor exists to hide.

DarkP2P does not try to work around this. When the page finds that the browser has no RTCPeerConnection, it tells the other peer to switch, and both use the relay. This also happens when only one of the two peers is on Tor.

How the relay keeps end-to-end encryption

The relay changes the route, not the encryption. Files are encrypted in your browser with AES-256-GCM before they are sent, using keys derived from the secret in the link's fragment, and that secret is never sent to the server. In relay mode the server receives those encrypted frames over the WebSocket and passes them to your peer, who decrypts them.

The server can see how much data is relayed and when. It cannot see the contents, the file name or the file type. Peers never learn each other's address in relay mode, because each of them talks only to the server. The server sees a Tor exit address for you, or no address at all on the onion service.

One limit is worth knowing: anyone who records the relayed frames and later gets the share link can decrypt them. See the threat model.

What to expect

  • Size. A room can relay 50 MB in total, counting both directions. With a Pro token on either side the cap is 500 MB. The budget lasts until both peers have left the room, so open a fresh link for the next transfer. The page refuses a file that does not fit before sending anything.
  • Speed. The relay limits each sender to about 1 MB per second (4 MB per second in a Pro room). Tor circuits are often slower than that, and then Tor is the limit.
  • Availability. The number of rooms relaying at once is limited, and all onion-service visitors share one connection allowance. At busy times the page may report that the relay is busy, or fail to connect. Try again a little later.
  • Memory. The offer shows whether the file will be streamed to disk or buffered in memory. If Tor Browser does not give the page disk storage, the file is held in RAM until it is complete, which the relay's size cap keeps within reach.
  • Pro tokens. A token is kept in the browser's local storage. Tor Browser clears that when it closes or when you request a new identity, so keep a copy of the token.
